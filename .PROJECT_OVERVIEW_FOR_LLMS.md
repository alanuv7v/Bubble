# Bubble: design intent

This note captures the product direction and recurring engineering preferences that can be inferred from the project. It is deliberately about principles, not a map of the current files: implementation details will change, while these choices are more useful context for future work.

## What Bubble is trying to be

Bubble is a personal, lightweight interface for conversations with language models. It treats a conversation as something the user can shape: chats have people or characters ("Bubbies"), and model behavior can be configured. The product direction is closer to a flexible, user-owned workspace for AI conversations than to a single-purpose chat box or a hosted social service.

The project aims to make this experience available across browser and desktop environments, while keeping application data on the user's device. These are goals, not a claim that every runtime or deployment path is finished. When describing current capability, check the implementation; when making design decisions, preserve the broader direction where practical.

## Product and architecture principles

### Keep the user in control

Local ownership is a defining intention: conversations and configuration should belong to the user and remain under their control. Using an external model still means sending the relevant request content to that provider, so local persistence and private inference are separate concerns. Avoid designs that quietly require a central Bubble account or server to own the user's data.

### Make model behavior configurable

The model, endpoint, request parameters, character/persona, and conversation context are treated as separable pieces. This keeps the interface adaptable to different models and providers and lets users shape how a conversation behaves. Prefer explicit configuration and composable data over baking one provider, model, or persona into the product's core.

### Represent the domain as connected things

Chats, participants, messages, prompts, and model configurations have distinct identities and relationships. That separation suggests the project is intended to support reuse and recombination: a character or configuration should not have to be copied into every conversation just to use it there. Preserve meaningful relationships and history when extending the data model; avoid collapsing independent concepts into opaque chat blobs without a clear reason.

### Favor a small, understandable implementation

The project repeatedly favors direct, lightweight code and clean boundaries over adopting a large framework or abstraction layer by default. Existing conventions explicitly prefer snake_case for most names, early exits where they improve clarity, and generally discourage classes. Keep additions easy to trace from user action through domain behavior to persistence or a provider request. Introduce abstraction when it removes real duplication or complexity, not as ceremony.

### Keep the core adaptable across environments

Browser and desktop support are part of the direction. Platform-specific storage and filesystem behavior should be kept at clear boundaries so product concepts do not become needlessly tied to one host. Do not assume that a detected runtime is fully supported just because the project has a path or configuration for it; verify the actual implementation before making claims.

### Prefer user-facing utility over infrastructure for its own sake

The application is meant to help people have and manage conversations. Persistence, streaming, configuration, editing, and presentation should serve that experience. Choose the simplest implementation that preserves user data and makes the interaction understandable; avoid expanding infrastructure without a concrete product need.

## Guidance for future changes

- Preserve local ownership, user-configurable model behavior, and the separation between conversations, participants, and provider configuration.
- Treat cross-platform support as an architectural aim, while describing shipped behavior accurately.
- Follow the existing lightweight style. Reuse project patterns when they are clear, but do not preserve a pattern merely because it exists if it makes the code harder to understand.
- Keep data flow and side effects visible, especially when sending conversation content to an external provider or changing stored data.
- Distinguish established behavior from aspirations and partially implemented ideas. The code and current UI determine what works today; this document records the inferred intent behind the project.

## Basis and limits

These principles are inferred from the project's original description (a lightweight LLM chat interface with locally stored data, browser and desktop targets, and OpenRouter-based API access), its repeated separation of conversation/persona/configuration concepts, its movement toward cleaner modular code, and the repository's explicit coding conventions. They are guidance for interpretation, not a fixed specification. If a future explicit product decision conflicts with this summary, follow the newer decision.
